# Ссылки и разрешение имён

## Цель

Различать hard link и symbolic link и понимать, как имя превращается в объект файловой системы.

## Prerequisites

`05-Filesystems-and-Inodes.md`.

## In scope

Hard link — дополнительная запись имени, указывающая на тот же inode. У inode увеличивается счётчик ссылок, а данные остаются доступными, пока существует хотя бы одно имя или открытый descriptor. Hard link обычно нельзя создать между файловыми системами и для каталогов.

Symbolic link — отдельный inode, содержащий путь к цели. Он может пересекать файловые системы и указывать на несуществующий объект. Поэтому удаление цели превращает ссылку в dangling link.

```text
hard link:      имя A ─┐
                       ├── один inode ─── данные
                 имя B ┘

symbolic link: имя link ─── путь ─── другой объект
```

Символическая ссылка разрешается при каждом обращении. Относительная ссылка интерпретируется относительно каталога, в котором находится сама ссылка, а не текущего каталога вызывающего процесса. Это часто объясняет ошибки после перемещения дерева.

## Диагностика

```bash
ln original hard-link
ln -s original symbolic-link
ls -li original hard-link symbolic-link
readlink symbolic-link
readlink -f symbolic-link
find -L /path -type l
```

Одинаковый inode у `original` и `hard-link` подтверждает hard link. Для symbolic link `ls -l` показывает путь, а inode ссылки отличается от inode цели.

## Типичные ошибки

- считать symbolic link копией файла;
- использовать абсолютную ссылку внутри переносимого deployment bundle;
- забывать проверить dangling links;
- удалять имя и ожидать немедленного освобождения места при открытом файле.

## Практика

Создайте оба вида ссылок, измените содержимое через каждую, переместите каталог с относительной symbolic link и объясните результат.
