# Пользователи, группы и identity

## Цель

Понять, как Linux идентифицирует субъект операции и как UID/GID участвуют в проверке доступа.

## Prerequisites

Процессы, пути и файловая система.

## In scope

Процесс имеет real/effective credentials: UID, GID и дополнительные группы. Владелец файла и группа сравниваются с credentials процесса при проверке permissions. `root` обычно имеет расширенные полномочия, но capabilities, namespaces и security policy могут ограничивать результат.

Локальная identity хранится через NSS-слой. Источник может быть `/etc/passwd`, LDAP, SSSD или другой backend. Приложение не должно предполагать, что пользователь всегда описан только локальным файлом.

Пользовательские и сервисные аккаунты должны иметь минимальные права, предсказуемый lifecycle и владельца. Общие аккаунты ухудшают аудит: невозможно определить, кто выполнил действие.

```bash
id
getent passwd app
getent group docker
ps -o pid,euid,egid,cmd -p "$PID"
```

`sudo` меняет effective identity на время конкретной команды и должен использоваться с ограниченным набором разрешённых действий.

## Типичные ошибки

- путать имя пользователя с UID;
- добавлять сервис в широкую группу «для исправления доступа»;
- использовать `root` для приложения без необходимости;
- забывать, что уже запущенный процесс не всегда получает изменённые группы;
- менять `/etc/passwd` вручную без понимания NSS.

## Диагностика

Сравнивайте `id` интерактивной сессии, credentials процесса, владельца ресурса и effective permissions. При SSH и automation учитывайте, под каким пользователем реально выполняется команда.

## Практика

Создайте отдельного сервисного пользователя, назначьте минимальную группу для чтения каталога, проверьте доступ от имени пользователя и через `sudo`.
