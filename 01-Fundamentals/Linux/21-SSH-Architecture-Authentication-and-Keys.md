# SSH: архитектура, аутентификация и ключи

## Цель

Понять, как SSH строит защищённый удалённый канал и чем отличаются authentication пользователя от проверки host identity.

## Prerequisites

Процессы, users/groups, permissions и базовый TCP.

## In scope

SSH состоит из client и server (`sshd`). После установления TCP-соединения стороны согласуют алгоритмы, создают зашифрованный transport и проверяют host key. Затем клиент аутентифицирует пользователя: паролем, public key, certificate или другим разрешённым методом.

В public-key authentication приватный ключ остаётся у клиента, а публичный ключ хранится на сервере в `authorized_keys`. Клиент доказывает владение приватным ключом, не передавая его серверу. Права на приватный ключ должны исключать чтение другими пользователями.

`known_hosts` хранит ранее подтверждённые host keys. Предупреждение о смене ключа может означать переустановку сервера, смену адреса, ошибку DNS или атаку посредника; без проверки нельзя механически удалять запись.

`ssh-agent` временно предоставляет ключи клиентским процессам, но сам агент становится чувствительным ресурсом. Forwarding агента включают только для доверенных цепочек.

## Базовая схема

```text
ssh client
  ├── проверяет host key
  ├── устанавливает encrypted transport
  └── доказывает владение private key
          ↓
      sshd → authorized_keys → shell или command
```

## Типичные ошибки

- копировать приватный ключ на сервер;
- отключать host key checking без threat model;
- давать ключу чрезмерные права;
- использовать один ключ для всех людей и automation;
- считать успешное TCP-соединение успешной аутентификацией.

## Практика

Создайте отдельную пару ключей для лабораторного пользователя, добавьте public key через `authorized_keys`, проверьте права и удалите доступ без изменения серверного пароля.
