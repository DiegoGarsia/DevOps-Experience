# Текстовые потоки и обработка данных

## Цель

Научиться строить прозрачные CLI pipelines и обрабатывать текст так, чтобы результат можно было объяснить и повторить.

## Prerequisites

`02-CLI-and-Command-Execution.md`.

## In scope

Unix-подход строится вокруг небольших программ, каждая из которых читает поток и выдаёт поток. `stdin`, `stdout` и `stderr` — независимые каналы. Pipeline соединяет stdout одной команды со stdin следующей:

```bash
journalctl -u nginx --no-pager | grep -i error | sort | uniq -c
```

Такой pipeline удобен, если каждая стадия имеет понятный контракт. Но текстовый парсинг хрупок: изменение формата, локали или пробелов может сломать автоматизацию. Для JSON следует применять `jq`, для YAML — специализированный parser, а не цепочку `grep`.

Полезные операции:

- фильтрация строк;
- выбор полей;
- сортировка и агрегация;
- подсчёт совпадений;
- проверка контекста вокруг события;
- нормализация timestamp и идентификаторов.

## Безопасный pipeline

При диагностике сохраняйте исходные данные до обработки. Сначала убедитесь, что поток не пустой и соответствует ожидаемой схеме, затем применяйте фильтры. Иначе команда может вернуть пустой результат, который будет ошибочно принят за отсутствие проблемы.

При обработке логов учитывайте:

- часовой пояс;
- переносы строк внутри stack trace;
- повторяющиеся события;
- чувствительные данные;
- размер входного файла.

## Типичные ошибки

- использование `grep` для разбора вложенного JSON;
- потеря stderr при перенаправлении;
- отсутствие кавычек вокруг переменной;
- фильтрация слишком рано и потеря контекста;
- предположение, что порядок логов равен порядку событий в распределённой системе.

## Практика

Создайте журнал с несколькими уровнями, timestamp и request ID. Постройте pipeline, который считает ошибки по сервисам, а затем измените формат одной строки и найдите, какая стадия перестала работать.
