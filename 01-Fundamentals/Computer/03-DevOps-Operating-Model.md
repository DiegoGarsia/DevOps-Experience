# Операционная модель DevOps

## Цель

Понять DevOps как способ уменьшать время и риск доставки изменений, а не как название должности или набор инструментов.

## Prerequisites

`01-Computer-Systems-Model.md` и `02-Data-Representation-and-CLI.md`.

## In scope

DevOps соединяет разработку, эксплуатацию, безопасность и бизнес-цели через короткий проверяемый feedback loop:

```text
Изменение → сборка → проверка → доставка → наблюдение → обратная связь
```

Технические практики поддерживают этот loop:

- version control делает изменение воспроизводимым;
- automation уменьшает ручные операции;
- immutable artifact отделяет сборку от окружения;
- observability показывает фактическое поведение;
- progressive delivery ограничивает blast radius;
- incident learning превращает сбой в улучшение системы.

DevOps не означает, что один человек должен знать всё или что production можно менять без контроля. Зрелая практика делает ответственность явной, изменения обратимыми, а качество проверяемым до и после deployment.

## Основные trade-offs

- Больше автоматизации требует вложений в тесты и стандарты.
- Более быстрый release без наблюдаемости увеличивает риск.
- Immutable infrastructure упрощает повторяемость, но требует управления образами и состоянием.
- Сильная изоляция уменьшает blast radius, но усложняет диагностику границ.

## Антипаттерны

- ручной production hotfix без записи изменения;
- «мониторинг» только по доступности процесса;
- pipeline, который проверяет сборку, но не проверяет deployment;
- перенос ответственности между командами вместо общей измеримой цели;
- автоматизация нестабильного процесса без сначала определённых критериев успеха.

## Проверка понимания

Объясните, почему rollback, observability и version control являются частью одной операционной модели, а не независимыми инструментами.
